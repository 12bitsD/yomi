# 飞书单任务卡：实现路径、平台边界与验证门槛

> 阅读定位：本文件保留截至 **2026-09-28** 的研究证据与候选比较；**2026-09-29 已完成方案收敛**，最终选择和开发契约以 [已确认技术方案](../chat-flow-technical-design.md#final-review-decisions) 为准。本文历史候选不是新的待决策项；路线获批仍不等于能力或端到端效果已验证。

核验日期：2026-09-28。范围：本地 yomi 源码与飞书官方文档；未创建远端卡片、未发送消息、未调用模型、未做客户端 E2E。本文件是技术方案的证据输入，不修改已确认的 D1–D12。

## 1. 先给结论

有效期内，最值得验证的是 **JSON 2.0 卡片实体 + 稳定组件身份 + 非打字机模式的局部更新**。它能把动态状态与阅读正文拆开更新，仍是同一条主任务卡消息；文档明确存在这些 API，但没有承诺局部更新保留用户的折叠选择，必须实测。

发现一项先于实现的硬边界：**官方规定，卡片实体从创建起 14 天失效；消息卡发送后只有 14 天可更新、30 天可触发请求回调。** 它不是“连续 14 天未使用”才失效。传统 IM PATCH、立即回调更新也不能据文档绕过。因而“永远同一飞书 message_id，持续更新和控制、任意久后恢复”不能按当前公开契约承诺。Provider Session 长期保留和 Thread 消息继续路由是不同能力，不能用它们掩盖旧卡不可更新。

本文保留两个同代单卡的呈现候选，它们都受上述期限约束。2026-09-29 已确认 N8-A 为优先验证路线，并选择 L1 修订 D12：每任务一张当前有效主卡，同代跨轮复用、跨期限换代，旧卡保留历史。L1 的具体规则以 [最终方案 §8](../chat-flow-technical-design.md#l1-review-decision) 为准；N8-B 与每轮结果卡都不是自动兜底。

## 2. 必须分清的对象与契约

| 对象 | 定义与承诺 |
|---|---|
| 主任务卡消息 | 一个 task 的当前有效飞书 message_id；同代入口不随 Run 变化，跨期限按 L1 换代。历史代次仍定位原任务；Thread 输入直达原 Provider Session。 |
| 卡片实体 | 飞书 CardKit card_id，用于组件更新；不同于消息 ID、task ID、Provider Session ID。保存创建时间与有效期，不能当永久资源。 |
| 当前执行状态 | 当前 Run、队列暂停状态、等候用户的请求及最后确认时间。状态来自执行控制器；卡片发送失败不能反向改成任务失败或完成。 |
| 已发表结果 | 一个明确 Run 的权威正文、结果判定、未完成项、产物入口。发布后不被后轮覆盖；若需修正则有可识别版本。 |
| 过程 | 进度和工具活动，独立于权威正文。不能以“最长文本”“所有折叠内容”替代结果判定。 |
| 展开选择 | 用户的阅读状态；与共享业务状态分开。JSON 2.0 只支持共享卡，不证明折叠点击会同步，也不证明服务端可读到个人选择。 |
| 显示版本 | 本地希望展示的版本与平台最后确认版本分别记录；不可因请求已发出就认定用户看到最新状态。 |

最小数据契约应包含：task/run/result 的稳定关联；message_id、card_id、实体创建时间；状态版本和单卡更新顺序；各逻辑区组件身份；结果正文的稳定读取入口；平台投递状态。按钮同时带目标 task、必要时的 run/request、操作和版本，后端重新核验权限及当前对象。它们是表达职责的字段，不要求本文给代码结构。

## 3. 节点一：创建卡片与跨轮布局

目的：进入任务时找到唯一入口；完成一轮以后继续同一 Session，看到的旧结果与当前运行不会混淆。

发散时比较：每轮一张卡、不断追加整篇到一张卡、单卡只留最新结果、单卡有有界历史。每轮一张已被 D12 排除，无界追加受容量限制排除。以下是同一代卡片内部的研究比较；期限换代遵循 L1，不属于按轮多卡。

| 候选 | 怎么开发 | 效果与代价 |
|---|---|---|
| A：固定阅读区域与历史索引，推荐首选 | 一次建立稳定的任务标题、状态/控制、结果、过程、历史入口。当前运行与上轮结果有各自 Run 标识。新轮开始不清空既有结果；历史全文保存在权威结果存储，卡面只保留有界索引。 | 常用路径最短，卡片大小可控。若自动换成最新结果，会替换用户正在读的内容；实现需明确展示的轮次，至少允许固定选中的历史轮次，不能把某轮引用解释为另一轮。 |
| B：同卡有界的逐轮折叠记录 | 每轮在原卡内增加“第 N 轮结果/过程”区域；保留最近若干完整条目，较早条目变成带 Run 标识的全文入口。 | 各轮关系直观、旧结果不需立即换页；组件和字节增长快，要更早移出正文，并验证删增区域不影响已展开的其他区域。 |

两个方案都需要先完成卡片入口与任务绑定的可恢复记录，再允许真正执行；发送结果不确定时先核对投递状态，不因重试建立第二张主卡。不在本文假定飞书发送 API 的幂等范围，开发时按选用发送接口规范验证。

## 4. 节点二：持续更新与展开态

目的：用户展开正文或过程后，不被后台刷新反复收起；进度和停止控制仍可见。

发散包括整卡重建、保持组件 ID 的局部更新、服务端接管展开状态、暂停所有显示更新。整卡重建的旧路径不能证明满足 R3；冻结全部显示会损害真实状态。保留：

| 候选 | 怎么开发 | 效果与代价、可行条件 |
|---|---|---|
| A：原生折叠 + CardKit 局部更新，最终 N8 已选验证路线 | 正文与过程分别用原生面板，稳定 element_id；刷新仅改状态组件或面板内具体正文，不重建面板，不反复写 expanded。采用 streaming_mode=false 的组件更新，合并高频事件。 | 点击直接由客户端处理，阅读自然；无需为每次展开联网。**原生点击有无回调、各端在子组件变化后是否保留展开态，文档没有保证**，必须通过门槛测试。 |
| B：显式“展开正文/过程”按钮 + 服务端视图状态 | 用两组明确的按钮控制对应内容显示；点击后记录显示选择，与状态一起渲染，连续更新沿用该选择。无须推测原生面板的不可见状态。 | 阅读选择可重建，调试确定性较强；点击有网络往返和失败状态，且 JSON 2.0 共享卡意味着服务端改出的显示选择对所有读者生效。它是**卡片级共用选择**，不是每个人的私有偏好；若要求群内个人独立阅读，则不能作为等价替代。仍需验证刷新视觉与折叠语义满足 R3。 |

不建议首版为了打字机效果开启 streaming_mode：局部更新无需它；官方要求交互时先关闭流式模式，流式模式 10 分钟自动关闭，增加停止/提问按钮与生成状态协调。可在基本单卡契约验收后单独评估。

## 5. 节点三：当前状态、已发表结果与历史轮次

目的：用户能同时理解“现在发生什么”和“上一轮完成了什么”，不会把上轮成功误看成当前成功。

两个方案都先持久保存结果正文和关联，再发表终态投影；若无最终正文，仅展示已知终态和原因，不编造报告。摘要由明确的结果信息生成，执行状态以控制器证据为准。

| 候选 | 怎么开发 | 取舍 |
|---|---|---|
| A：当前状态固定，结果默认显示最近发表轮次 | 下一 Run 运行时，保留并标明“上轮结果：R3”，动态区显示“R4 执行中”；R4 发表后更新结果区，历史入口保留 R3。 | 常用状态一眼可见，步骤少。阅读中的正文可能在发表时变化，必须明确轮次并提供固定历史轮次的入口；不要宣称这种布局天然保留阅读位置。 |
| B：当前状态固定，结果只按显式选择切换 | 首份结果默认打开；后续有新结果时状态区提示“R4 结果可读”，已选 R3 保持，用户点击才切换。 | 正在阅读的正文稳定，但每轮多一次选择。服务端切换共享卡会影响其他读者；多用户场景更适合让历史入口打开稳定正文，而不是更改全卡的共享选择。 |

推荐先采用 A 的简洁默认 + 可明确引用的历史入口；若验收发现发表时打断阅读，再评估 B，不能伪称原生折叠态回调可以自动识别“正在读”。

## 6. 节点四：超长全文、引用和回读

目的：卡片可浏览，全文不丢，Agent 回答追问时读到对应结果而非摘要或日志。

发散过整篇硬塞、静默截断、分页、附件、文档。前两者不满足需求；分页会将共享页码与阅读状态耦合，首版不推荐。保留：

| 候选 | 怎么开发 | 取舍 |
|---|---|---|
| A：稳定的全文文件/附件，最终 N9 已选 Markdown 附件 | 先按 Run 保存 Agent 原始正文和归属元数据，再导出完整 Markdown 结果；接近平台预算时卡面保留摘要与完整文件入口。附件是结果，不是新主卡。上传失败要明示“全文入口尚不可用”，不能称已经交付全文。 | 额外接入少、正文快照明确、方便下载。移动端阅读与分享弱于在线文档，需要验证附件权限及后续可访问性。 |
| B：稳定的全文文档/只读结果页面 | 每轮结果有稳定地址，卡内显示摘要、轮次和入口，权限沿用任务阅读范围。内容由权威结果导出，不能独立漂移。 | 长文、代码和历史导航阅读更好；多一个服务/文档权限与失败处理环节，维护和部署成本更高。 |

**回读契约独立于这两个显示选择：** yomi 自己的卡片引用优先解析到 task/run/result 后读权威正文；不从截断卡面反推全文。保留过程与结果分界，不把全部 collapsible_panel 内容递归塞回模型。外部卡片采用明确可识别的结果区域契约，未知区域保守处理。

仅引用长期变化的主卡 message_id，飞书不保证携带用户当时所见的 Run 版本。因此历史入口/附件必须含稳定 Run 标识。若用户引用未指明轮次且卡片已跨轮改变，系统必须披露/确认对应轮次，不静默取“现在最新一轮”冒充当时所读结果。此问题不能仅靠增加正文提取器解决。

## 7. 节点五：平台故障、重试与长期使用

目的：断网或回调重试不造成重复任务、倒退状态、误操作；平台投递故障不伪装成执行结果。

| 候选 | 怎么开发 | 取舍 |
|---|---|---|
| A：同卡串行投递，合并中间态，推荐 | 同卡只有一个更新者；中间进度合并成最新快照，停止受理/等待用户/终态优先。每次操作带递增 sequence 与幂等标识，保存最后确认版本。遇到限流/交互占用退避，失联后读取业务快照再投递；不重放每条过期进度。 | 结构较小、用户看到有意义变化；不保证每个中间进度都显示，这不等于业务事件丢失。需区分提交不确定与确定失败，验证重试的幂等行为。 |
| B：持久化投递任务逐项确认 | 持久记录待投递的语义变化和投递凭证；重启后按版本恢复，允许合并纯进度，但必须确认关键状态的显示结果。 | 跨进程投递更可追踪，但存储/重放状态复杂；不能把“显示投递恢复”误写为恢复旧执行队列。 |

两者共同约束：3 秒内回调响应仅说明受理或拒绝，不提前宣布已停止；回调重复、乱序、跨 Run 均重新校验；旧版本不得覆盖新版本。更新不可用时保留真实结果与状态，必要时在同一 Thread 发简短故障提示/提醒；普通更新故障不自动新建主任务卡，期限场景则按已批准 L1 执行换代。已有代码的“PATCH 失败后纯文本兜底”不能直接继承为新主卡策略。

**期限不是重试可以修好的错误。** 实体到期、消息超过 14 天、按钮超过 30 天要识别为平台能力限制。官方未声明同 message_id 换绑新 card_id；IM PATCH 请求只说明卡片 JSON/模板且仍有消息年龄限制。创建新实体再换绑旧消息目前只是未获支持的假说，不进入承诺。最终 L1 已明确允许因期限产生新一代主卡；必须如实表现为入口换代，并遵守原任务/Session/运行状态不变的契约，不能宣称仍是同一物理消息。

### 7.1 长期边界：L1 已确认，保留两项历史比较

研究时发现平台期限与“永久同一物理卡”冲突，因此提出以下两项需求调整。用户已于 2026-09-29 选择 L1，D12 已同步修改；L2 未选。此处保留取舍背景，不再要求重新确认 L1。

| 候选调整 | 用户实际得到什么 | 取舍与仍需验证的点 |
|---|---|---|
| L1：按期限换代，保持一个逻辑任务入口，已选 | 同一个 task、Provider Session 和任务历史不变；活跃或等待回答时在最早适用更新期限前、空闲时在用户下次返回后，新建一代当前主卡，旧卡保留可追溯记录，旧 Thread 输入仍能定位原任务。不按每轮生成结果卡。 | 大多数时候保持原生飞书操作；但历史中会有多代物理卡，用户会看到换代消息，不再是永久同一 message_id。原 Thread 内发新卡能否保持最自然入口、旧按钮拒绝/导向行为、多个代际去重与路由必须实测。 |
| L2：固定入口指向长期任务页面，未选 | 飞书保留一个长期存在的静态入口卡，点击普通链接打开可持续更新的任务页面；同一 Session 的状态、控制、历史和阅读偏好由该页面管理，Thread 输入仍可路由。 | 入口消息可以不变化，页面不受卡片更新窗口约束；但实时状态和控制迁出飞书卡面，需要额外页面、身份校验与移动体验。静态链接不同于请求回调，实际客户端可用性需验证，不能承诺卡面仍实时更新。 |

L1 只解决长期入口的产品选择，不证明其实现或同代展开态已通过验证。换代须先发布/定位新卡，再切换唯一当前映射；不新增 Prompt/Run、不解除暂停，保留同进程队列及当前请求；旧主卡控制拒绝，独立问题消息按其原请求是否仍有效处理。原 Thread 连续性、发送不确定去重以及新卡阅读体验仍须按最终方案验收。

## 8. 开发前置门槛与验收顺序

1. **实现已选期限契约**：按 L1 保存消息发送时间与实体创建时间，以较早的适用更新期限安排活跃任务换代，空闲任务由用户返回触发。验证身份、队列、暂停和当前请求保留；不以持续刷新冒充续期，不再次把已批准选择当作待确认。
2. **最小真卡实验**：固定正文和过程两个面板，稳定组件 ID；PC、iOS、Android 记录版本。覆盖子正文增长、状态刷新、终态、停止、新 Run、新结果、重连、重新打开、多读者各自展开。优先验证已选局部更新 A；只有具体证据表明 A 无法满足时才评审其他路线，B 不自动启用。无测试结果不标为通过。
3. **交互不被生成阻塞**：运行中点击停止、回答问题，与组件更新竞争；证明请求及时受理且更新不复原。首选非流式模式。
4. **容量与回读**：长中文、多代码块、深链接、附件上传失败；超过预算仍能取得全文。分别引用当前结果、历史附件和缺少轮次的主卡，验证不串轮、不把过程当结果。
5. **重试与期限**：模拟乱序、重复点击、限流、未知提交结果、服务重启；真实老卡验证 14/30 天边界须有平台证据/历史测试资源，不能靠修改本地时钟伪造平台年龄。

方案选择已闭合，但没有单卡原型与 L1 换代验收证据，仍只能标记“已选方案、效果待验证”，不能宣布 R3/D12 已实现或完整技术可行。
