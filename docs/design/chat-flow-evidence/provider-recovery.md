# Provider 接入与恢复：技术流程评审依据

> 阅读定位：本文件保留截至 **2026-09-28** 的研究证据与候选比较；**2026-09-29 已完成方案收敛**，最终选择和开发契约以 [已确认技术方案](../chat-flow-technical-design.md#final-review-decisions) 为准。本文历史候选不是新的待决策项；路线获批仍不等于能力或端到端效果已验证。

日期：2026-09-28。本文是技术方案的研究输入，历史推荐及候选比较不另行打开已确认决策；受 [需求基线](../chat-flow-requirements.md) D1–D12 约束。核查范围：本地仓库、官方在线文档、Kimi Code 2.0.2 精确版本源码；未启动模型、未接飞书、未验证集群与真实恢复。本文不涉及代码接口或序列化格式。

## 1. 不再重新选择的边界

- 一张任务卡固定一个 Kimi Code 或 Codex Session，跨轮复用；Kimi 使用 ACP，Codex 使用 App Server，本地 stdio 是第一接入路径。
- 卡片 Thread 原始 prompt 直接交给绑定 Session；普通聊天只读进度。当前轮问答/授权回复与下一轮 prompt 是不同输入。
- 每卡单写入、独立队列与暂停。运行实例可以释放，Provider 历史和卡片绑定保留；查看不调用模型。
- 重启或已验证的升级后，用户可主动从原卡恢复同一 Session；旧等待队列、暂停状态和中断运行不自动恢复执行。
- yomi 不管理 Git 工作区；只记住恢复参数并检查所指向的原目录仍可用。指定目录不是创建 worktree，也不代表文件隔离。

## 2. 核心语义与总契约

**Adapter** 是把 yomi 的执行意图翻译成 Provider 原生协议、再把原生事实翻译回来的边界。它不另行决定任务成功、把用户输入改写成 prompt、为旧 Run 自动重试，也不变成第五种扩展端口。接入服务优先通过现有 Source/Sink/Gate/Capability 使用通用运行契约；状态进入现有 sqlite/config 管理范围，不建私有状态孤岛。

**Provider Session** 是可继续的上下文身份；**运行实例** 是当前承载它的进程/连接/内存状态；**Run** 是一次用户输入对应的执行尝试。释放实例不等于删除 Session；resume 是载入历史供新 Run 使用，不是恢复被杀掉的测试进程。

所有操作须包含同一组可追踪含义：谁发起、针对哪张卡及绑定 Session、是否针对指定 Run/待回复请求、对应哪个入站消息或操作、当前连接是哪一次连接、输入与附件引用、采用哪份已验证 Provider 配置。跨 Provider 不强求原生字段相同，但关联不能丢。Kimi 没有和 Codex 完全对称的 turn 标识时，由 adapter 关联唯一在途 prompt 与 yomi Run，不能捏造原生 ID。

| 契约面 | 对调用方的承诺 |
|---|---|
| 能力与版本 | 启动协商协议和能力，返回已验证的创建、恢复、问答、授权、附件、取消范围、历史读取与释放能力；缺少必需能力拒绝启动该任务，不默默改用非交互或自动批准 |
| 创建/恢复 | 返回精确原生身份和恢复所需条件；创建成功且绑定持久化后才允许发送第一个 prompt。恢复必须回到原身份；不存在、版本不兼容、原目录缺失、认证未就绪分别说明 |
| 新一轮输入 | yomi 受理只代表本进程记住了队列项；获得调度资格并向 Provider 投递不等于已经执行。只有 Provider 的启动事实才进入执行中；某些协议响应直到终态才返回，不能把“写入管道成功”当作启动确认 |
| 运行事实 | 进度、工具、等待请求、正文片段、原生终态均绑定指定 Run。区分实时事件与历史重放；重放只补读视图，不重新发送通知、输入、授权或触发新执行 |
| 当前轮响应 | 回复关联原请求、原 Run、原连接代次和回答者，校验仍可回答且权限匹配；重复同一回答返回已有处置，不重复放行；矛盾回答拒绝。Provider 确认已处理前只显示已提交 |
| 停止 | 明确目标 Run，先使本卡暂停生效，再向该 Run 请求取消。受理、取消中、原生终态、受控工作已退出分别可见；超时/断线显示未确认并阻止同 Session 下一次写入 |
| 读取 | 读取持久化快照/结果不提交 prompt；返回事实更新时间和完整性。需要 Provider 历史时使用其读取或载入机制，不把查询升级成新执行 |
| 释放 | 仅在 Run 终结且相关输出已保存后释放 live resources；不删除历史。若持久化或收尾未确认，不能宣称已具备可靠恢复条件 |
| 错误与重试 | 明确区分拒绝（未执行）、可重试读取错误、输入是否启动未知、运行失败和已中断。结果未知的执行请求不得盲重发；先查事实，仍不确定就留在待核对状态 |

幂等性是 yomi 对重复消息/按钮的去重与状态约束，不能声称本地数据库和两个 Provider 之间存在跨系统原子事务或网络 exactly-once。持久化操作身份及已知结果用于防重，不意味着保存了可重放的旧待执行队列。

## 3. 节点一：统一适配边界

**目的：** 上层只有一套任务/运行流程，新增 Provider 或原生能力时不改动所有卡片与控制逻辑，同时不过度设计插件平台。

发散考虑过完全透传原生协议、只取两者最小公约数、统一核心加能力扩展、完整统一所有原生方法。收敛为以下两项；完整统一范围过大，最小公约数会丢掉双向交互价值。

| 方案 | 怎么开发 | 效果与代价 |
|---|---|---|
| A. 统一行为核心＋显式能力扩展（推荐） | 统一创建/恢复/新轮输入/响应当前请求/取消/读取/释放；每个 adapter 声明其能力限制。Provider 特有选项保留在其命名空间，未被上层理解的内容不参与通用状态推断 | 卡片与调度不依赖原生方法名，第三种 Provider 可按契约接入；需要为差异写明确映射和契约测试，但无需实现所有 Provider 功能 |
| B. 统一生命周期外壳＋Provider 专属执行流程 | 卡片只认最少身份/状态/结果，其余问答、停止收尾、版本判断由两条 Provider 流程分别实现 | 首次接线更直观，原生新功能可快用；两套流程容易形成不同停止/重试语义，上层每增加交互都要兼顾两种适配 |

推荐 A 的验收：同一套输入/暂停/回答/恢复场景对两个 adapter 都成立，差异通过能力声明表现，不靠猜协议；不在 v1 增加任意 Provider 插件市场、动态远程执行平台或自动 Provider 切换。

## 4. 节点二：首次创建与后续 Resume

**目的：** 用户看到的同一任务永远对应原会话，创建一半失败、绑定保存失败或恢复失败均不会导致隐式换 Session。

发散考虑卡创建就建 Session、真正执行时才建、每轮新建后塞历史、使用最近 Session。后两者违反绑定承诺，保留前两者。

| 方案 | 怎么开发 | 效果与代价 |
|---|---|---|
| A. 获得执行资格后创建/恢复（推荐） | 卡/任务先记录选定 Provider 与接入配置，状态为等待。获得资格后验证能力与原目录；首次创建取回原生身份，先持久化绑定再发 prompt；后续恢复精确身份再新建 Run | 排队或暂停中的卡不占用 live Session；首次启动可能稍慢。卡刚创建时要能表达“尚未启动”，不能伪造 Session ID |
| B. 卡创建时预建 Session、执行时才发 prompt | 创建卡的流程中先建并绑定 Provider Session，不调用模型；排队时允许卸载，正式执行再恢复 | 尽早发现凭据/目录问题，所有已就绪卡都有原生 ID；会产生用户从未执行的空会话，多一段创建/释放成本与孤儿绑定处理 |

共同逻辑：第一条 prompt 之前必须完成绑定落盘；若 native create 已成功、响应丢失，不能把猜到的最近会话绑定过来，也不反复新建。先只读找回可证明的同一创建结果，无法证明就标记初始化未确认，不执行。允许人工清理孤儿会话，但 yomi 不默默清历史。

后续新 prompt 在本卡排队，轮到它时验证旧 writer 已结束；加载同一 Session 后才发输入。Kimi 2.0.2 的恢复使用原工作区身份，additionalDirectories 不会在 load/resume 时加入；临时 MCP 配置需要接入侧明确重供，不能以为所有客户端参数已被 Provider 永久保存。

验收：两轮原生身份相同、Run 不同；重启后仍相同；故意移走历史/目录应明确失败；只看卡片和历史不产生模型请求。

## 5. 节点三：进程与连接生命周期

**目的：** 保留上下文不要求每张历史卡一直占内存；停止一张卡不能为省事杀掉其他卡的运行。

发散考虑每轮进程、每卡永久进程、每活跃卡实例、共享 Provider 服务池。永久进程浪费空闲资源，每轮强启停可能损伤相邻输入体验，收敛为两项。

| 方案 | 怎么开发 | 效果与代价 |
|---|---|---|
| A. 每张活跃卡独立 Provider 实例，空闲后回收（推荐首版） | 以原生双向 stdio 协议运行；相邻排队输入可复用实例，Run 终结且无待处理当前请求/受控工作后进入可回收阶段，保存结果再优雅收尾。下一次输入重新启动并恢复原 Session | 单卡异常、进程树强制收尾范围明确，更容易满足互不误伤；多张并发卡各占一个 Provider 进程，启动/恢复有代价，需要并发上限。此隔离不等于文件隔离 |
| B. 每种 Provider 共享一个或少量服务实例 | 一个服务承载多个 Session，按 Session 路由事件/请求，空闲时用原生 close/unsubscribe；服务仅在所有所属 Session 可安全收尾时重启 | 减少启动与重复内存成本，适合活跃卡很多的阶段；服务崩溃影响多卡，某卡失控时不能直接杀共享进程，必须依赖经验证的按 Session 取消/清理能力 |

共同契约：空闲回收无业务删除副作用；正在等用户回答仍属于当前 Run，不能为了省内存自动关闭。不要承诺瞬时释放所有内存；Codex 共享服务最后订阅者退出后，官方当前说明需 30 分钟无活动才卸载该 thread。独立进程策略可控制自己管理的树，但不能保证外部 MCP 作业和刻意脱离管理的远端进程也停止。

最终 N4 选择 A，N10 选择终态保存后按短空闲期回收；暂停但仍有等待项时也可释放 Provider，yomi 队列和暂停不变。B 保留为未来候选，不属于当前交付。统一行为契约可兼容未来实例策略演进，但当前实现必须遵守已选隔离语义。异常收尾沿用 yomi 现有进程树工具。

## 6. 节点四：当前轮提问与授权

**目的：** 当前轮需要你的回答时可以继续；你的新要求仍按既定规则下一轮执行，不混淆两者，也不把协议差异静默压平。

发散考虑读取用户话术猜用途、所有回复进队列、所有回复 steer、结构化请求入口。前三项有死锁或误投风险，只保留明确关联入口的两种实现。

| 方案 | 怎么开发 | 效果与代价 |
|---|---|---|
| A. 统一请求视图＋能力限制（推荐） | 把请求展示为提问/授权、选项、允许回答者、作用范围与有效状态；每次答复携带该请求的不可混淆关联。支持已声明的表单控件，Provider 专属范围按原义展示 | 交互一致，易验收重复和过期；需要单独映射“本次同意”“本 Session 同意”“拒绝”“取消”等不同效果；不支持的自由输入明确提示，不制造支持 |
| B. Provider 专属请求面板，统一响应路由 | 主卡显示等待与入口，问题由该 Provider 的专属交互内容呈现，响应仍严格关联原请求和原 Run | 能保留更多原生特性，适合后续加入特殊表单；用户在两个 Provider 间看到不同表达，卡片适配与测试数量增加 |

推荐 A 只统一能准确表达的部分：Kimi 2.0.2 的 form 支持多题/多选，但 Other 自由文本尚不支持；不能在卡片加一个输入框就声称后端接得住。Codex 支持的会话级授权要在按钮文案说明授权范围；不把单次批准升级为以后自动批准。

时间语义：默认跟随 Provider 请求生命周期，未回答继续等待；若 Provider 给出有效期限则原样体现。不会因为 yomi 本地等久了就批准。未来可加显式可配置的超时取消，但那是中断而不是回答。停止、Provider 结束/撤销、旧连接失效后禁用旧请求；只读重连发现同一待处理请求仍存在，才能重新开放回答入口。重启不自动重放旧批准。

响应不走 prompt 队列。收到用户回复仅显示“已提交”，Provider 的请求解决通知/相关工具继续执行等事实到来才确认已处理；回执丢失先核对，不能重新发送相反授权或把回复改造成下一轮文本。

## 7. 节点五：绑定、历史与结果保存

**目的：** 原卡可恢复，旧结果可稳定回读；数据库里有一个 Session ID 并不代表原上下文与结果都还在。

发散考虑只存 ID、复制全部 Provider 内部文件、读取时临时从模型总结历史、保存应用所需事实并保留 Provider 原存储。前者不满足恢复与结果唯一性；复制内部文件让适配绑定未公开格式；模型总结不能代替原正文。收敛为：

| 方案 | 怎么开发 | 效果与代价 |
|---|---|---|
| A. 保存关键事实与权威结果，Provider 管原生历史（推荐） | yomi 保存任务/卡/Thread/Provider 原生身份与恢复位置、配置版本、Run 对应关系和已知终态、待请求的展示事实、每轮完整结果及附件入口、入站/操作去重凭据。过程事件按需要留有限记录；Provider 历史留原目录 | 保存量可控，旧结果回读不依赖 Provider 当前是否在线或历史是否已压缩；必须把“执行终态”“结果保存成功”“卡片展示成功”分开处理 |
| B. 完整应用可见事件日志＋投影结果 | 持久化收到的应用可见输入与事件，明确重放边界、连接代次和稳定 Run 关联，由日志重建状态/结果；Provider 原生历史仍另存 | 更利于诊断、纠错与重建卡片；事件体量、隐私面、重放规则和格式升级成本更高。不能因此重放用户指令或自动恢复旧队列 |

推荐 A 保留足以恢复可信状态的关键事实，不保存每一 token 和所有内部推理。完整结果的权威正文由 yomi 按 Run 留存；Provider 原历史用于下一轮上下文，两者职责不同。卡片只是投影视图，更新失败可以从同一正文重投，无须再次调用模型生成结果。

储存顺序：创建/恢复绑定完成后才启动；运行终态到来后保存最后事实与权威正文，再更新卡片。卡片投递失败不会回滚已发生的工作；保存失败则显示“本轮结束，结果保存失败/待处理”，不能声称已可靠保存。磁盘写失败应阻止继续开展无法留下可恢复记录的新 Run，并说明原因。

队列仍是 yomi 队列所属进程内的承诺，关闭独立 Provider 进程不影响它：持久的消息去重/操作记录要能识别“此前已受理，但重启后不再保留”的旧消息，避免平台重送时自动开始。此记录不是可调度队列，不允许靠重建它绕过 D2/D9。

## 8. 节点六：断线、重启与升级

**目的：** 通信异常后不把未知说成成功或失败、不重复执行；普通重启保留继续对话能力。

发散考虑自动重发所有请求、重启时重放队列、自动接管原 Run、只恢复事实后等待新输入。前两者不符合共识；自动接管需区分“观察还活着的执行”和“重跑已中断执行”。最终两项：

| 方案 | 怎么开发 | 效果与代价 |
|---|---|---|
| A. 事实核对，确认旧 writer 退出后按新输入恢复（推荐首版） | 断线标记未确认，停止派发同卡下一轮；查询 Provider 或检查本卡受控实例。进程/容器重启后读绑定与最后事实，旧非终态记为中断或未知，按已验证收尾确认无旧 writer；用户新 prompt 才 resume＋新 Run | 行为简单、避免重复副作用；短暂断线也可能让该次 Run 中断，用户需要明确新发一次。可以自动只读核对和修复视图，但不自动重发 prompt |
| B. 有边界的连接重附着，不能证实时退回 A | 若同一 Provider 服务仍存活且协议能证明原 thread/turn 与未解决请求身份，重新订阅/读取，继续观察原 Run，不重新投递；证据不齐、stdio 子进程已死或服务换代时退回 A | 短暂观察连接故障更平滑；两 Provider 的重附着/历史可恢复范围不对称，需要更多活性核查与竞态处理。stdio 管道断开通常不能像网络服务那样直接重新接回原管道 |

推荐 A 不是一断网就把状态置失败。Provider 到模型的重试由 Provider 自己处理；yomi 到 Provider 的通信失去确认才进入未知核对。恢复前认证、版本、原目录、原生历史和单写入所有权全部具备才允许新输入。

升级路径：固定 yomi 与两 Provider 的精确版本；升级前停止受理新执行并按部署流程收尾；保留原卷与目录；备份绑定/结果与 Provider 历史；目标版本通过恢复回归后才标记支持。出现格式不兼容不静默新建，不宣称任意降级都可读新格式。部署等待队列不跨重启；必须在使用说明/队列界面表达，而不是升级后假装成功处理。

下游接入必须提供持久化历史与原目录、可复现的固定 Provider 安装、运行时/凭据/配置接线及普通重建和目标升级验证；已有部署条件不等于恢复能力已验收，更不构成无中断升级承诺。责任与现有能力缺口统一见 [下游接入边界](../chat-flow-context.md#downstream-integration)，云端开发无需访问私有部署源码。

## 9. 节点七：停止、超时与实际收尾

**目的：** 点击停止后确实不会偷偷开始下一轮；既有文件改动保留；状态与受控工作是否退出一致。

发散考虑只显示已停、协议取消后立即杀所有 Provider 进程、无限等待原生终态、分阶段停止并验证。前两种会伪报或误伤。收敛为：

| 方案 | 怎么开发 | 效果与代价 |
|---|---|---|
| A. 原生取消＋有界验证＋本卡进程树兜底（推荐，与独立实例组合） | 先暂停本卡、固定目标 Run；发取消，等终态并核对受控委派/终端；超过配置的收尾窗口仍活跃时，按本卡受控进程树升级终止；无法核对的外部工作明确列出 | 对慢工具和卡住的本地执行有可操作兜底；强制退出可能损失最后少量未落盘输出，但不回滚已有文件。兜底只能用于确实属于本卡的树 |
| B. 原生取消＋保持停止未确认，等待修复 | 同样立即暂停并精确取消；超过窗口后保持未确认、禁下一轮，提供诊断与外部处置入口，不自动强杀 | 更适合共享 Provider 服务，避免打断其他卡；单卡可能长时间不能恢复，必须有后续运维处理路径，不能只留一个永远转圈按钮 |

共同契约：取消回执不等于已停止。Codex 要等指定 turn 的 interrupted/其他终态，Kimi 要等在途 prompt 的 cancelled/对应终态，再核对实际受控工作。Kimi close 是 best-effort teardown，不可当作进程树全部退出的证明；Codex 当前官方另有 experimental 的 thread background terminal 清理接口，必须纳入能力核验而不能假设 turn interrupt 自动等于所有后台任务全停。

若目标 A 自然完成、B 尚未开始，暂停照样生效，A 记录其真实完成；若 B 已经开始，旧 A 的停止请求不得改指 B。强制终止前后保留停止意图与最后事实，迟到事件只能补证据，不解除暂停、不改变新 Run。

恢复队列是允许尚未开始的输入按原序调度；已停止 Run 的新尝试由用户明确新发 prompt，不承诺原指令位置续跑。

## 10. 开发顺序与验收门槛

1. **先固定能力与语义**：冻结两个版本，书面列清上表能力/错误/确认条件；不支持的交互先明确。协议协商、创建/恢复、只读和关联用最小 adapter 验证，不接 UI 掩盖缺口。
2. **建立最小恢复闭环**：首次建 Session→持久绑定→一轮结果保存→释放→同一身份恢复→第二轮；在每个边界模拟进程退出，验证不新建替代、不自动重做。
3. **接入双向等待与控制**：问答、授权、拒绝、重复回答、迟到回答、等待时停止；同一 Provider 两张卡并行时停止一张不影响另一张。
4. **补持久化与异常事实**：断管道、Provider 崩溃、磁盘满、结果已保存但卡片投递失败、创建响应丢失、终态丢失；每种都明确是否执行和哪些事实未知。
5. **验证 nika 重建及目标升级**：真实保留数据卷、旧卡继续同一 Session；旧等待队列不重跑、旧审批不重放、原目录缺失准确失败。涉及真实调用由后续实施测试执行；本报告不把静态资料视为通过。

不应开始承诺的效果：任意 Provider 版本可升级、无限逐字历史、一次停止可覆盖所有远端服务、0 延迟/0 资源的 resume、两个平台完全对称、跨网络恰好一次执行。
