## 要实现的体验与关键约束

- 普通 Chat 保持文字风格。nika Skill 和专用执行入口首版都能创建任务，共用一套能力、权限与受理契约；不能只交付 Skill 提示词。
- 每个逻辑 Task 固定一个 Kimi Code 或 Codex 原生 Session。任务 Thread 后续 Prompt 保留原文、附件和引用，直接进入该 Session，不让 Chat 代写。首版不切换 Provider，不管理 Git/worktree 或文件隔离。
- 同 Task 新 Prompt 串行排队；当前轮原生问答/授权返回原 request，控制走独立路径。各任务暂停/停止/恢复隔离，共享有限执行名额。
- 停止先暂停派发，保留等待项及已有改动；确认实际停止前只显示“停止中/未确认”。提前恢复返回受阻，不能预约自动续跑；确认后显式恢复只继续 B/C，不重试已停止的 A。Harness 不因代码冲突或业务失败额外暂停/编排。
- Kimi 使用 ACP，Codex 使用 App Server，本地 stdio 起步并固定版本。活动 Session 独立 Provider 进程，相邻轮次可复用，空闲安全保存后释放；后续新输入恢复原 Session。同一 Session 首版不支持被其他客户端同时写入。
- 关键事实持久化并形成当前快照；进度查询可读历史、原始指令和结果，但不向 Execution Session 提交 Prompt、不创建 Run。运行终态、业务成功、显示同步和恢复可用性分别表达。
- 每个任务一张当前有效主卡，同代跨轮局部更新，正文与过程可分别展开。L1 因平台期限换代保持 Task/Session/Run/请求/队列/暂停，不执行新任务；旧主卡控件失效，固定问题消息按原请求有效性判定。每轮新增结果卡不在已选方案内。
- 按 Run 保存 Agent 原始完整正文与归属信息，不重写回复；超限首版提供 Markdown 全文附件。历史入口绑定结果轮次/版本，不从可变主卡引用猜用户要读哪轮。
- 历史、绑定、原目录不自动删除。归档不等于删除。普通重启与已验证升级支持用户主动续接；yomi 旧等待队列/暂停状态不跨进程恢复，不自动重跑旧 Run。仅 Provider 进程重启则保留 yomi 进程内队列。
- 输入重送、旧回调、未知派发、停止超时和显示失败遵循统一契约；未知执行先核对，卡片或附件投递失败只重试显示，不重跑任务、不换新 Session。

## 开发方式与跨仓库交付

按技术方案 P0–P7 推进：先复核当前代码和目标版本，做 Provider/平台关键能力最小验证；随后贯通创建、输入、运行、结果、停止/恢复，再扩展异常、多卡、重启升级及真实客户端验收。并行开发独立模块可以，但模块各自完成不等于用户流程完成。

每阶段在 `docs/design/chat-flow-implementation-status.md` 记录对应需求/节点/契约、实际改动、检查命令及结果、证据位置和仍欠的验收。新增实现设计可以下沉到代码/API；继续保持原需求和已确认语义。优先写对顺序、归属、重复、取消、恢复有判别力的测试，不用仅证明 mock 会返回成功的测试替代真实契约。

- **yomi 交付**：W1 通用控制、W2 事实与结果、W4 通道/任务路由，以及 W5 中属于 runtime 的恢复契约；遵循 Source/Sink/Gate/Capability 四端口，不新增第五套扩展系统或另一份权威队列。
- **nika/接入方交付**：W3 的两个真实 Provider Adapter、Skill 与专用入口业务接线、版本配置，以及 W5 的数据保留和集成/升级验证。具体职责见 [下游集成](chat-flow-context.md#downstream-integration)。
- **缺下游访问时**：完成可独立实施的 yomi 能力、通用测试接入与集成说明，明确列出下游所需接口、改动、版本及验收依赖；不能把下游代码藏进 runtime、用模拟 Adapter 冒充真实双 Provider，或宣布整个任务卡功能完成。获得对应 checkout/权限后继续补齐这些目标。

## 验证门槛与外部环境

先遵循 [AGENTS.md](../../AGENTS.md) 的检查要求，提交前运行 `just ci`。修改 prompt 装配、conductor、cron 等触发对应 harness 回归；通道行为还要真实飞书链路验证。命令失败或缺依赖要保留具体结果，不写成通过。

真实环境验证前阅读 [yomi-e2e](../../.agents/skills/yomi-e2e/SKILL.md) 的隔离约束。该文件的机器路径和账号是原环境示例，不是云端已有授权配置。每条测试 yomi 命令都要显式配置独立的 `YOMI_CONFIG`、`YOMI_DATA_DIR`、`YOMI_SOCKET`；运行 [harness-e2e.sh](../../evals/harness-e2e.sh) 还需独立 `YOMI_DB`，该脚本有真实模型调用。使用用户提供并授权的测试凭据与目标，不能命中默认/生产 daemon；公开提交不得包含凭据、真实用户消息或内部配置。

至少为以下门槛分别留下证据：

1. 双入口创建、同 Task 多轮直达、两 Task 不串上下文/控制、原生问答不死锁。
2. A/B/C/D 队列场景、停止与换轮竞争、停止超时不续跑、暂停有队列时释放 Provider 后仍保留队列、恢复不重试 A。
3. Kimi 和 Codex 分别通过创建、固定身份绑定、真实取消及关联执行停止范围、保存/释放、原 Session 恢复、请求失效、未知派发核对；一个通过不代表另一个通过。
4. 飞书桌面/手机、两读者的同代展开态与跨轮阅读；L1 活跃/待回答/暂停队列/空闲返回换代、旧控件校验、原 Thread 路由。平台真实期限用历史卡/平台证据验证，改本机时钟不能证明。
5. 原始全文与 Markdown 超限导出、历史版本回读、输入/回调去重、卡片显示失败及重启不重放。
6. 普通重启与明确版本的升级恢复、历史/目录缺失、单写入约束，以及普通聊天和旧命令兼容。

有些环境或平台事实只能在授权测试目标上验证。缺凭据或能力时继续不依赖它的开发，列明具体未验证项、影响与所需条件；首版真实验收仍是未完成。若原生平台确实无法满足既定效果，附最小复现和替代方案后提出必要选择，不自动换卡片模型、Provider、授权方式或恢复语义。
