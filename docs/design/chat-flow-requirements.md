# yomi 对话与执行任务体验需求

状态：v1 需求共识已收束，含 D1–D12；完整技术方案已评审收敛，实施与交付入口见 [云端 handoff](chat-flow-handoff.md)。本文描述目标行为，不表示技术实现、平台验证或端到端验收已完成。

确认日期：2026-09-25～2026-09-29（09-29 补充 N1 双入口及 D12 期限换代）。范围：yomi 的执行控制能力及飞书通道呈现，接入方以实际任务验证。

技术评审入口：[开发流程、行为契约与取舍](chat-flow-technical-design.md)。2026-09-28 研究发现飞书已发送卡片的 14 天更新/30 天回调期限；2026-09-29 用户选择 L1，D12 已调整为每任务一张当前有效主卡，因平台期限允许换代，原任务与 Session 不变。证据、实现边界和待完成验收见该方案 §8。

## 1. 目标与阅读方式

让用户在同一聊天入口中自然地讨论问题、交办工作和查看结果：普通交流保留现有文字体验；执行任务有持续可辨认的任务卡，能够查看进度、展开结果、停止执行并管理后续队列。

本文定义用户应得到什么行为，以及怎样判断需求被满足。行为契约与开发路线由 [已确认技术方案](chat-flow-technical-design.md) 统一规定；API 及代码模块等可逆实现细节在开发中落实。此前开发计划中的实现建议不自动升级为需求；旧计划中的跨重启队列持久化建议由 D2 取代。

## 2. 核心概念

| 概念 | 本文含义 | 需要避免的混淆 |
|---|---|---|
| 普通交流 | 问答、解释、方案讨论，以及为回答问题进行的资料查询 | 回复长、耗时长或使用工具，不等于执行任务 |
| 执行任务（task） | 用户交办的一项实际工作，例如修改代码并运行测试 | 一项任务可能经过多轮运行、等待和补充 |
| 任务卡（task card） | 用户看到的主任务入口，绑定一个 Provider Session；当前有效卡承载状态、结果与控制，按 D12 可因期限更换消息代次 | 换卡不更换 Task 或 Session；卡片消息身份不是任务身份 |
| 一次运行（run） | 系统实际执行的一轮或一次尝试 | 运行结束不等于任务完成 |
| 会话（session） | yomi 现有输入与执行队列的组织单位 | 整个会话不等于一项任务；现有队列中的输入也不全是 coding 任务 |
| Provider Session | 任务卡绑定的 Kimi Code 或 Codex 上下文，接收任务卡 Thread 的原始 prompt | 首版任务卡生命周期内固定 Provider，不在卡内切换 |
| 任务卡执行队列 | 属于逻辑 Task／yomi 执行会话的后续输入，按序执行；当前卡只提供入口 | 换卡不重建队列或解除暂停；不同任务不共享暂停状态 |
| Chat Session | 普通交流、跨任务提问和只读任务状态查询 | 不能代替用户修改 Provider Session |
| 待执行队列 | 本卡已受理、尚未开始执行的输入 | 已停止的当前执行，不自动视为待执行项 |

用户应能识别任务及其控制范围；不要求用户理解内部 session/run，也不据此引入新的通用任务管理系统。

本文“本卡”“每卡”的执行与控制范围指背后的逻辑任务及执行会话，不指某一代飞书消息。换代保留同一作用域，队列跨进程保留范围仍按 D2，不因卡片可恢复而扩大。

## 3. 需求

### R1. 普通交流保留文字体验

日常问答、解释、检索后回答和方案讨论保持原有文字呈现与已经调整好的回复风格。普通长回答也不因长度自动改成任务卡。

这里的“文字”指用户看到的呈现，不约束飞书底层必须采用哪一种消息格式。该改造不重写普通回答，不要求模型套用任务报告模板。

**验收：** 短问答、长解释、检索后回答和方案讨论均保持普通文字；单凭使用工具或耗时较长不会出现执行任务卡。

### R2. 执行任务具有明确的进入和结束边界

用户交办 coding、测试等实际工作并开始执行后，进入任务卡呈现。同一个任务跨多轮运行、等待或补充时，用户仍能认出它是同一项工作。本轮执行结束后保留卡片与 Session 绑定；任务 Thread 内的新 prompt 继续使用该 Session，任务 Thread 外的普通讨论保持文字呈现。

2026-09-29 的 N1 评审确认：首版同时具备 nika 通过 Skill 调用任务创建能力、专门声明执行任务的入口，两者共用创建契约。专用入口无须普通 Chat 再判断是否执行；权限、原文与背景交接、Provider 固定、重复创建与失败反馈保持一致。入口的具体界面不在本轮限定。来源与开发逻辑见 [技术方案 N1](chat-flow-technical-design.md#n1-review-decision)。

一个任务只有一张当前有效主卡，各轮结果有明确的 Run 关联及唯一权威正文。按 D12 在同一有效代次内更新状态和结果，跨期限允许更换当前卡，不为每轮结束另发独立结果卡；历史结果仍须可辨识和引用，不能将不同轮次混成同一结果。旧代卡留作历史；必要提醒、待用户操作信息和完整正文附件可以另发，不构成另一张当前主卡。

**验收：** 普通聊天中的“讨论怎么改”保持文字；“按这个方案开始改”进入任务卡；中途补充和多轮执行仍能关联到原任务；任务 Thread 外的解释性追问不继承卡片模式。在原任务 Thread 内追加 prompt 不会改投 Chat Session。

### R3. 卡片支持快速浏览与完整阅读

卡面直接展示当前状态、简要说明或结果摘要、关键未完成事项及可用结果入口。执行中显示已知进展；结束后给出结果、未完成部分与产物。信息尚未产生时，不编造摘要、产物或完成比例。

完整正文与执行过程分别展开，短结果可以直接展示。按单卡方案实现持续更新，用户已经选择的展开/折叠状态不因刷新、正文增长、完成或停止而被重置。需验证飞书可用的更新方式；若无法满足，报告具体现象、限制和影响后再对齐，不自动切换每轮独立结果卡，也不将选择单卡理解为接受展开态反复重置。

完整结果可访问、可引用。超出单卡容量时，提供清楚的完整正文入口，例如附件或文档；不能静默截断后仍称为完整结果。用户引用折叠报告继续提问时，应能读取结果正文，而不是只有摘要或混入执行日志。

**验收：** 不展开即可知道状态与关键结果；正文和过程独立展开；同一有效代次内任务卡消息持续更新，多轮执行不另发独立结果卡。桌面及手机分别验证展开选择经连续更新、正文增长、完成、停止和下一轮运行仍保留，记录更新方式与客户端。跨期限换代单独验证入口连续性，不能以允许换代为由忽略同代展开态要求；不预先承诺客户端个人展开偏好能迁移到新物理卡。超长中文/代码结果可完整取得，引用对应轮次的结果不会丢失正文。当前未完成客户端实测，不能据方案选择宣称跨客户端或关闭重开后的展开偏好已经能够持久保留。

### R4. 状态与实际执行结果一致

用户能区分执行中、等待用户输入、完成、部分完成、失败、正在停止和已停止。具体名称及状态组合留给技术方案，不要求直接照此建立一个枚举。

任务成功依据整项工作的结果与验证，不能仅凭一次运行结束、委派返回成功或发出最终回复判断。失败或部分完成时说明影响和剩余事项；需要用户输入时提供明确入口。

**验收：** 完成了代码修改但测试失败，不显示整项任务成功；等待输入不误报仍在执行；任务卡的结果与所关联 Run 的状态一致，旧轮次的完成状态不冒充当前任务状态。任务完成和执行停止分别表达。

### R5. 停止当前执行，反馈真实范围

执行中的任务有明确的停止入口，用户能看出停止作用于哪一项工作。系统区分停止请求已受理、正在停止与已确认停止。

停止范围包含与该任务关联、由系统管理的委派执行。实际工作仍在运行、停止超时或无法确认时，界面如实显示未确认的状态，不能提前显示已停止。其他任务或会话不受误操作影响。

停止保留已经产生的文件改动和结果，不自动撤销、回滚或删除它们。外部执行能否停止须以接入验证为准；对不受控的工作明确说明范围，不能承诺全停。

**验收：** 点击后有受理反馈；关联执行实际退出后才确认已停止；慢工具、委派进程和迟到结果不会导致误判；保留已经产生的产物。

### R6. 停止后保留并暂停待执行队列

选择停止本卡当前执行并暂停后，本卡原待执行项的内容、附件、身份和顺序保持完整；它们不会接着自动开始。暂停期间发给本卡的新执行输入可以进入队列，但不能绕过暂停执行。其他任务卡的运行、队列和暂停状态不受本次操作影响。

队列的暂停状态与待执行内容可查询。恢复必须来自明确操作，按照保留顺序继续；重复点击、消息重试和后台执行的迟到通知不能绕过暂停。

暂停的是本卡执行队列，普通聊天仍可问进度、讨论和提问；发给本卡的新执行请求保持排队，普通聊天不能顺带恢复执行。保留承诺仅覆盖同一个 yomi 运行进程的生命周期；重启、崩溃或升级换进程后的队列和暂停状态不在首版保存承诺内。界面或使用说明应明确这一限制，不能暗示待执行项已持久保存。

恢复队列只启动仍在等待的项。已经停止的 A 保持已停止；要继续或重试 A，由用户另行明确发起。新一次尝试可使用已有改动与上下文，但首版不承诺从原执行点续跑。

系统不能为了做到保留而重新拼出只有文本摘要的消息。停止与同卡运行切换同时发生时，停止对象不能漂移：尚未开始的项不得越过已经生效的暂停；若 Run B 已经开始，应反馈实际对象与状态，不能把 Run A 的停止请求自动套用到 B。停止尚未确认时，不应启动该 Session 的下一轮写入。

**验收：** 在同一 yomi 运行进程内，卡 X 的 Run A 执行、输入 B/C 等待时停止，B/C 内容及附件完整保留；普通聊天问“现在什么进度”仍能回答而 B/C 不启动；发给 X 的新输入 D 排在后面。明确恢复 X 后继续 B→C→D，不丢失或重复启动，A 不自动重试。卡 Y 的执行、队列和暂停状态均不被 X 的操作改变；Y 仍受正常资源调度约束。重启后的状态保存不纳入首版验收。

### R7. 新能力有清楚的作用范围与兼容边界

控制入口指明实际任务或队列范围，沿用相应操作的权限要求。过期的卡片、重复回调或另一项任务的状态不能误控制当前工作。

新任务呈现及暂停能力能够按接入配置启用。普通对话与未启用场景保持原行为；现有取消、清空、继续等操作不被悄悄赋予另一种含义。新旧客户端不兼容时给出明确反馈。

**验收：** 不影响其他会话；旧卡片不能误停止新任务；关闭新能力后原场景仍可用；新操作遇到不支持的运行时不会伪报成功。

## 4. 已确认的首版边界

以下十二项由用户于 2026-09-25～2026-09-28 明确选择，约束技术方案及首版验收。

| ID | 用户选择 | 需求含义 | 对技术方案的约束 |
|---|---|---|---|
| D1 | 普通聊天继续，执行队列暂停 | 暂停后仍能问进度、讨论和提问；发给本卡的新执行输入排队 | 不能冻结整个聊天入口；按 D11 隔离每张卡的队列和控制范围 |
| D2 | 首版只保证本次运行期间保留 | 同一个 yomi 运行进程中，待执行项及暂停状态保持；重启、崩溃、升级后不承诺恢复 | 首版不要求队列持久化与跨重启恢复；“本次运行”不是单次模型调用或单个任务 |
| D3 | 继续 B/C；A 另行重试 | 恢复队列不自动重做已停止的 A | 区分队列恢复和任务重试；首版不要求 A 的无损断点续跑 |

### D4 任务卡 Thread 直接进入 Provider Session

任务卡是执行任务的用户入口。用户回复任务卡 Thread 时，原始 prompt 直接进入该卡绑定的 Kimi Code 或 Codex Session；普通 Chat Session 不负责改写、代转或隐式修改执行任务。Chat Session 可以通过只读状态视图回答进度，但读取状态不唤醒执行。

### D5 一张任务卡固定一个 Provider Session

任务卡创建时绑定 Kimi Code 或 Codex 之一。任务卡生命周期内不提供 Provider 切换；实现保留 provider/session 引用抽象，未来 handoff 不进入首版流程。

此处任务卡指主任务入口。按 D12，同一有效卡跨多轮更新状态与结果；因期限更换卡片代次时，也始终保持原任务及 Provider Session 的绑定。

### D6 本轮结束后保留 Session，回卡发消息时恢复

用户已于 2026-09-28 确认：本轮执行完成且历史保存后，可释放该任务运行实例，卡片显示“本轮已完成，可继续”，保留 Provider 和 Session 绑定。只打开卡片不启动模型；在同一卡片 Thread 发送新 prompt 时，沿用相同 Session ID、新建 Run ID，并遵守队列调度与暂停限制。归档仅收起入口，不等同于删除历史或工作区。

Resume 续接已保存的对话上下文，不承诺复原被停止的进程或无限逐字历史；历史不可用时应明确报告恢复失败，不能静默新建空 Session 冒充续接。保留期限及跨部署恢复边界见 D8–D9，D2 的待执行队列保留范围不变。证据与代价见 [Session 保留与恢复评估](provider-session-lifecycle.md)。此前“一起结束”的表述保留在历史来源，由 D6 取代其永久关闭含义。

### D7 执行中追加 prompt 排在当前 Run 之后

任务 Thread 中，当前 Run 尚在执行时收到的新 prompt 保留原文与附件，排为同一 Provider Session 的后续 Run，不默认 steer 或打断当前 Run。同一个 Provider Session 不并发写入；当前 Run 结束后是否立即启动后续 Run 仍受本卡队列暂停状态及资源调度规则约束。停止仍使用明确控制入口；按 D11，暂停与恢复只影响本卡。资源并发上限及跨卡调度实现另行设计，不引入跨卡共享暂停状态。

该规则适用于用户主动追加的执行指令；coding agent 当前轮正在等待的提问或授权回复，按 D10 使用对应请求 ID 回送当前轮，不能排到当前轮结束之后。

### D8 历史和对应工作区不自动到期删除

首版不按空闲时间或归档状态自动删除 Provider Session 历史及其对应工作区。清理来自明确操作，需让用户知道会失去哪些历史、产物或恢复能力；本次需求确认本身不是删除任何现有数据的授权。该承诺是保留策略，不是无限磁盘或灾备保证。

### D9 普通重启和部署升级后可主动恢复旧卡

保留原数据卷、Provider 会话数据与原工作目录的条件下，首版支持 nika 普通重启或部署升级后，用户从原任务卡发新 prompt、恢复相同 Provider Session 并开始新 Run。卡片/Thread 与 Session 的绑定必须持久化；不能只把数据文件留在磁盘而失去入口映射。升级路径须验证 Provider 数据格式兼容性；数据卷损毁、明确删除、任意不兼容版本迁移不属于无条件恢复承诺。

本能力不恢复 D2 的旧待执行队列或暂停状态，不自动重跑中断任务。启动后的状态核对不得凭旧 running 字段显示任务仍正常执行；确认旧运行已退出或不存在冲突执行后，才可受理新的实际运行。中断及无法确认的状态应如实显示。只打开卡片、读取历史或重连事件不启动模型；恢复由用户的新执行输入触发。

### D10 使用原生双向协议接入 coding agent

Kimi Code 使用 ACP，Codex 使用 App Server；首版固定版本、优先本地 stdio，先验证会话创建/恢复、进度事件、停止及当前轮问答/授权回调，再接入任务卡。两者由 adapter 提供统一的上层契约，同时保留 Provider 能力差异；非交互 CLI 不作为功能不足时的静默降级路径。

用户对 Agent 当前轮请求的回答，通过该 task/run/request 的关联回送当前轮；过期请求不能批准下一轮操作，也不能自动转为新的 prompt。选用双向协议不增加额外业务审批，也不代表自动批准工具操作。无法提供的交互须明确反馈；能力事实、实验性及空闲卸载限制见 [协议取舍](provider-control-options.md)。

### D11 任务卡的队列和控制范围相互隔离

每个逻辑任务独立绑定 Provider Session，任务卡消息进入对应 Session；待执行队列及暂停状态属于逻辑 Task／yomi 执行会话，不属于飞书消息代次。停止、暂停和恢复只影响目标任务及其关联执行，不改变其他任务的运行或暂停状态，也不冻结普通聊天。同 Provider 下的不同 Session 同样遵守此边界，迟到事件与旧回调不能串到其他任务或新的 Run。按 D12 换卡只改变入口，不清空或重建本进程的等待项、不解除暂停，也不重放已停止的一轮。

这项隔离不要求每卡独立进程，不承诺无限并行，也不提供文件系统或 worktree 隔离。共享服务的资源并发限制仍可单独配置，但不能将某张卡的暂停解释为其他卡也被暂停。本卡控制入口不兼作整个聊天的批量暂停入口。

确认来源：[按卡隔离的用户确认](chat-flow-context.md#decisions-before-review)。早期草案将 Execution Lane 定义为“管理多张任务卡之间排队、暂停和恢复的执行调度范围”（state=superseded）；该定义未经用户确认，现由按卡队列定义取代。D1–D3 的暂停、保留和恢复语义不变，其 A/B/C 示例具体限定如下。

### D12 当前有效主卡持续更新，允许按期限换代

2026-09-29 用户明确选择 L1：**一个逻辑任务始终只有一张当前有效主卡；同一代卡在有效期内持续更新，跨平台期限允许更换，旧卡留作历史。** 跨多轮执行不按轮次新增独立结果卡，Provider Session、当前 Run、当前请求、输入队列及控制范围保持原身份；换卡本身不触发新 Run、不恢复 Session、不重放 Prompt，也不解除暂停。

空闲任务过期后在用户主动回来继续时换代；运行中或等待回答的任务应在最早适用的卡片消息／实体更新期限前换代。新卡确认可定位后才成为当前有效入口；发送不确定时先核对，不能因重试产生多个有效入口。换代失败如实标注呈现故障，不伪报任务失败或重新执行。

优先在原任务 Thread 发布新代卡，并维护旧、新入口到原任务的映射；新旧卡回复与当前请求的路由须实测，不默认另开 Thread。旧卡还能更新时可标注新入口，过期后不保证能再改写。仍能到达后台的旧控制需核对代次、任务、Run／请求，不能批准新操作；回调本身失效后，不承诺点击旧按钮仍能得到后台提示。

先验证单卡持续更新能否保留用户展开选择，包含可用的局部更新方式；不能仅凭当前整卡 PATCH 路径有问题就宣布平台所有方式均不可行。记录客户端、更新路径和结果，覆盖 R3 的正文增长、完成、停止及下一轮场景。单卡方案被选定不等于平台能力已验证；若不能达到要求，说明具体限制后再对齐，不自动切换多结果卡或接受展开态重置。

各轮正文保持唯一权威版本和明确 Run 关联；主卡显示当前状态与结果，历史内容可读取、可引用，具体入口由单卡技术方案设计。历史 replay、事件重送和投递重试不能制造冲突结果、让旧事件覆盖新状态或额外创建结果卡。失败、停止、部分完成仍如实标注；正文超限时的完整入口要求不变。

当前选择来源：[L1 期限换代确认](chat-flow-context.md#review-l1)。历史：[按单卡方案推进](chat-flow-context.md#review-l1) 中用户原文“按照单卡的方案来吧”保留；旧解释“永久同一物理卡消息”state=superseded，由本次 L1 取代该限制，同卡多轮和不按轮新增结果卡的要求继续有效。更早的每轮静态结果卡兜底仍为 state=superseded，保留于 [历史兜底选择](chat-flow-context.md#historical-result-fallback)，不因允许期限换代重新启用。

### 具体交互示例

1. 卡 X 的 Run A 正在改代码，同卡后续输入 B、C 已排队；卡片显示 A 的进展及可用的停止入口。另有独立任务卡 Y。
2. 用户在 X 点击“停止当前执行并暂停队列”（示意文案，非最终按钮名称）：A 进入停止中，X 的 B/C 保留并暂停。
3. 用户在普通聊天问“X 改到哪了”：正常文字回答已知进展，X 的队列仍暂停；A 真正退出后才显示已停止。
4. 用户在 X 的 Thread 又交办 D：D 加入 X 的等待队列，不立即执行。
5. 用户明确恢复 X 的队列：B、C、D 按顺序继续，A 保持已停止；若要重新做 A，用户另行交办。
6. 上述操作不改变 Y 的运行、待执行输入或暂停状态；Y 按自身状态和正常资源调度执行。

该示例发生在同一个 yomi 运行进程内。若期间重启，首版不承诺恢复其中的待执行队列及暂停状态。

## 5. 场景验收清单

| 场景 | 预期行为 | 对应需求 |
|---|---|---|
| 普通短问答、长解释、检索后回答 | 保留文字风格，不因长度或工具调用变成任务卡 | R1 |
| 讨论方案后开始修改并测试 | 从明确执行边界进入任务卡，进展与结果关联到同一任务 | R2、R4 |
| 长任务中查看进度和最终报告 | 同一有效代次内持续更新，正文与过程独立展开，更新保留展开态；未通过实测则报告限制，不自动按轮发卡；期限换代按 L1 | R3、D12 |
| 中途补充信息，任务经过多轮执行 | 逻辑任务身份不变，当前入口仅按 L1 因期限换代；每轮结果明确关联且正文唯一 | R2、D12 |
| Run A 结束后，同任务开始 Run B，随后更新、停止或结束 | 有效期内仍使用同一张任务卡消息，不为每轮新建结果卡；当前状态和各轮结果不混淆，保留用户展开选择 | R3、R4、D12 |
| 活跃、待回答或暂停队列的任务跨卡片期限 | 换代保持 Task/Session/Run/请求与本进程队列状态，不启动执行、不解除暂停；仅一张当前有效卡，新旧入口路由正确 | D2、D4、D11、D12 |
| 引用旧轮次结果、在原任务 Thread 继续，或只查看任务卡 | 引用能读回该轮正文，prompt 仍进入原 Session；查看不启动模型 | D4、D6、D7、D12 |
| 历史 replay、重复终态事件或结果投递重试 | 不产生冲突正文或额外结果卡，不让旧事件覆盖当前状态，结果仍关联正确 Run | R2、R7、D12 |
| 本轮完成后离开，再回到原任务发新 prompt | 保留原任务、Provider 和 Session ID；卡片过期则按 L1 换代，输入依原规则开始新 Run；无需 Chat Session 转发 | R2、D4、D5、D6、D12 |
| 只打开已完成卡片，或归档卡片 | 不启动模型；归档不删除会话历史 | D6 |
| 当前 Run 执行时追加 prompt | 内容和附件排到该 Session 的后续 Run，不默认打断；队列暂停时不启动 | R6、D7 |
| 原 Session 历史或工作区不可用 | 明确报告恢复失败，不静默换成新 Session | D6 |
| 长时间空闲或归档后再进入卡片 | 未发生明确清理时保留历史、绑定及工作区，不因到期而丢失恢复能力 | D8 |
| 保留数据卷和目录，重建 nika 或升级已验收的版本后回卡发 prompt | 原卡仍绑定相同 Provider Session；新 Run 可使用既有上下文；两种 Provider 分别验收 | D6、D9 |
| 运行或排队期间 nika 重启 | 旧 Run 标为中断或待核对，不凭旧状态报完成；旧队列不恢复、不自动重跑；不存在冲突执行后才启动新 Run | D2、D9 |
| Agent 当前轮等待用户回答或授权 | 卡片显示原生请求支持的交互；用户回复回到对应请求，当前轮得以继续；不将回复排到下一轮 | D7、D10 |
| 旧请求按钮重复、过期或执行已停止 | 不批准其他请求或新的 Run，不把旧回复转为新执行输入 | R7、D10 |
| 协议恢复时重播历史，或一端不支持某能力 | 历史不触发重复执行/投递；能力不足明确反馈，不自动批准或静默新建会话 | D6、D10 |
| 超长结果及引用结果继续提问 | 完整正文可取得、可回读，过程不混入结果 | R3 |
| 修改已完成但测试失败，或缺少用户输入 | 如实显示部分完成、失败或等待输入，不以单轮退出报成功 | R4 |
| 同一卡 X 的 Run A 运行，B/C 排队；停止时 A 恰好结束 | 停止对象不漂移；Run B 已启动则反馈实际状态，不能由针对 Run A 的旧控制请求默默取消 B；仍待执行的项保持暂停且不误删 | R5、R6、R7、D11 |
| A 的委派执行停止较慢 | 显示停止中或无法确认，不提前确认停止，不启动该 Session 的下一轮写入 | R5、R6 |
| 暂停卡 X 期间收到发给 X 的 D、旧按钮回调或后台通知 | X 的待执行项不偷跑，重复操作不重复恢复 | R6、R7、D11 |
| 卡 X 暂停期间普通聊天，并向 X 交办 D | 聊天可正常回复；D 排在 X 的队尾，B/C/D 均不因聊天而启动 | R6、D1、D11 |
| X 的 A 已停止后恢复 X 队列 | 只继续 X 的 B/C/D，A 保持已停止；另行明确重试才新建尝试；不改变 Y 的暂停状态 | R6、D3、D11 |
| 两卡使用同一种 Provider，停止或暂停 X | Y 不被停止或暂停，仍按正常资源调度执行；即使共用服务，也不把 X 的取消或迟到事件送给 Y | R5、R7、D11 |
| 同一进程中长时间等待，或准备重启 | 同一进程中保留内容与暂停状态；使用说明明确重启后不保证保留，不显示持久保存承诺 | R6、D2 |
| 未启用新能力或操作其他会话 | 既有行为与权限边界保持 | R7 |

## 6. yomi 与接入方的职责

| yomi 应提供 | 接入方应提供或验证 |
|---|---|
| 按实际工作选择普通回复或任务呈现的能力 | 哪些业务入口确实开始执行任务 |
| 任务卡更新、折叠、完整结果回读与容量兜底 | 任务说明、结果正文、产物与验收证据 |
| 可查询、可控制的执行与队列状态，支持普通交流与暂停执行分开处理 | 业务输入属于交流、执行或控制的明确意图，以及委派工作的关联关系与具体结果 |
| 可靠的停止、保留暂停和显式恢复行为 | 真实委派执行的取消传播与边界验证 |

通用能力在 yomi fork 开发并走 upstream PR/release，nika 消费固定版本；验证阶段可使用可定位的测试构建。业务策略及 Kimi Code/Codex 接入由 nika 维护，通过 yomi 的扩展契约接入；不能假定 nika 已有独立消息路由服务。仓库与发布关系的确认依据见 [yomi 与 nika 关系](chat-flow-context.md#repository-relationship)。

工作目录、Git 分支及是否使用 worktree 由用户/接入配置通过 Codex、Kimi Code 侧指定，不纳入 yomi 的工作区管理职责。yomi/adapter 只保存、传递和使用会话恢复必要参数（如原生会话 ID 和必要的 cwd），并反馈恢复错误，不创建、合并或清理 Git 工作区。D8/D9 的保留与恢复承诺由接入和部署保留原目录来满足；指定目录不等于保证多个 Session 的代码隔离。

呈现和调度能力可以分别交付。新的“停止并保留队列”入口，必须在底层语义及接入链路验证通过后启用。

## 7. 范围之外与技术方案输入

本需求不包含调整普通回复的人格/措辞、通用项目管理系统、任意任务优先级与拖拽排序、自动回滚产物、首版队列的跨重启持久化、已停止任务的无损断点续跑、一次性重写全部通道或生产部署。其他场景是否加入后续迭代另行确定。

yomi 自动创建/合并/清理 worktree、选择 Git 分支、管理跨任务代码依赖及提供文件隔离，也不在本次范围内。此前每卡独立 worktree 的建议未被采纳，不是实施前置条件。

以下是技术方案必须覆盖的问题，现已在对应节点、契约和验收中给出设计；开发时逐项映射 R1–R7 与 D1–D12：

1. 如何识别执行边界、关联任务与多轮运行，并让状态有可核验的来源。
2. 按 D12 设计单卡持续更新，验证飞书折叠控件及更新方式能否保留用户选择；若不能满足，说明具体限制、证据和体验影响后再对齐，不自动切换多结果卡。
3. 如何保证结果完整、引用可回读、超限可访问，以及投递失败后不会出现冲突结果。
4. 如何定义停止和任务切换的先后关系，覆盖委派取消、并发输入及迟到事件。
5. 根据 D1–D3、D11，如何组织各卡独立的执行队列、维护进程内暂停状态、保证同卡恢复顺序并处理旧命令兼容。如何识别已停止 Run 的后续补充，避免将旧 Run 的 steer 误注入下一轮或其他任务卡；资源调度不能改变按卡控制范围。
6. 如何测试上述场景，如何启用、灰度和回退，并清楚说明首版重启时的队列限制。
7. 如何将任务卡 Thread 稳定映射到 Provider Session，如何让原始 prompt 直达该 Session，如何通过统一的 provider/session 引用保留未来 handoff 扩展，同时不把 Provider 切换混入首版流程。
8. 如何区分本轮完成、运行实例释放、归档和删除，如何实现 D8–D9 的保留与跨部署恢复承诺；覆盖绑定持久化、版本兼容、原工作目录校验、恢复失败反馈和同 Session 单写入约束。
9. 如何实现两种原生双向协议的统一 adapter、能力探测、版本固定与请求关联；如何区分新 prompt、当前轮回答和控制命令，并验证取消与恢复的真实边界。

**后续交付：** 技术方案逐项给出 R1–R7 的实现边界和验证方式，并遵守 D1–D12。每项主要技术选择说明推荐、候选、代价与可验证效果；API 和模块等可逆实现细节由方案给出，不再逐项重复询问产品取舍。若平台能力或现有架构无法满足需求，先明确具体影响及替代选择，再调整需求，不能静默降低验收标准。

## 8. 研究依据

需求依据为本轮及此前已确认的体验讨论。既有研究基线为 yomi v0.10.39（`d70ae7cb`）及当时 main（`a8566269`），技术方案开始时需核对目标版本。

- 普通回复和观测卡存在不同渲染路径，但当前开关以 channel 为单位；任务呈现边界需要新增能力。
- 现有 cancel 会清空待执行输入，现有 mailbox 没有暂停/恢复语义；不能只修改按钮文案。
- 卡片折叠、刷新状态保留、完整正文回读及真实委派停止都需要各自验收，当前研究不代表这些新需求已实现。

查现有约定时读取 [通道面板卡契约](channel-panels.md)；调度、呈现和扩展实现遵循仓库 [AGENTS.md](../../AGENTS.md)。
